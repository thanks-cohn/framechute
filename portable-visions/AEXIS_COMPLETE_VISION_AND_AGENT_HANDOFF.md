# ÆXIS: portable vision and agent handoff

**Status:** Cross-repository product vision and staged proposal, updated 2026-09-24. This document describes aspirations and acceptance gates; it does not mark proposed features as shipped. Keep the same text in `Tiled-223D`, `substrate`, and `framechute` under `portable-visions/`. Read the local `AGENTS.md`, `Stages/README.md`, implementation handoffs, and code before changing any repository. The implementation and its tests outrank this narrative when describing present capabilities.

> **“My goal has always been endless possibilities for anyone who so dreams. So I hope the foundations I’ve laid may make your wildest visions and dreams come true.”**

## 1. What the creator is building

ÆXIS aims to be an inviting, mathematically and semantically legible world foundation for people, programmers, and authorized agents. A young artist can bring a few pictures and a description and receive a quick, beautiful, eerily close **editable** draft; an expert can specify geometry, styles, behavior, and scripts exactly. A person might eventually provide their own hundred-page book, several Tiled maps, annotated overhead and side views, and existing GLBs, and say: “Build my world in my format; make it expansive.” The system should do the repetitive interpretation, layout, and assembly while the author controls the result. It should eventually support characters, voices, mannerisms, interactions, games, animation, and new visual media. That long-range outcome needs many smaller proofs; neither a language model nor a picture guarantees faithful unseen geometry or a complete game today.

The emotional standard is **joy to use**: attractive defaults, quick visible results, tactile controls, small reversible changes, and room for extraordinary styles. Sun and moon placement could feel like moving lights in the sky; moving a landmass could feel like lifting and dropping a miniature world, with optional landing waves. These are creator-facing interactions backed by explicit data, not a requirement for expensive simulation. A creator must always be able to correct the inferred coast, height, asset base, camera angle, or character motion. The system's value is measured by how faithfully it preserves those decisions after save, reload, export, agent edits, and rendering changes.

Three complementary surfaces share the same world truth: (1) a direct visual interface for the artist; (2) a precise programmer API for exact operations and tests; (3) a bounded agent interface for discovery, inspection, planning, preview, and permissioned commit. Debug mode explains ordinary failures; opt-in deep debug exposes transforms, geometry, provenance, timing, and performance. The agent should have less guesswork because it can query actual terrain, heights, surfaces, anchors, relationships, and valid actions. A model is optional for basic import, editing, validation, rendering, and play.

The strategic product position is an **agent-legible, creator-controlled path through existing ecosystems**: Tiled for authored geography; Blender and other asset tools for 3D models; glTF/GLB for interchange; Godot as a first proposed downstream engine; ÆXIS itself for immediate browser world creation and eventually browser games. These ecosystems already interoperate in other products. An AI-accessible browser editor is not unique either. ÆXIS must earn adoption through a markedly easier and more dependable end-to-end experience, not through an exclusivity claim.

## 3. Current baseline and honest limits

The Tiled-223D standalone Vite/Three.js experiment contains a procedurally generated 500 × 500 two-island sample, Tiled JSON import, separate elevation, cheap batched land/ocean/sky treatment, flight, horizontal wrap, an optional ship GLB with fallback, and a wake-up placeholder. Its curvature or folded view is aesthetic: present wrap is a **flat repeated/toroidal approximation**, not a physical sphere. The Tiled extension's `.sworld.json` output is not yet a verified full round trip into the browser importer. The `Additions` insertion path produces a bounded low-ground experiment, not arbitrary mountains, every Tiled format, or a complete map editor.

World API v1 provides independent programmer and agent entry points over a shared schema-v1 terrain-region project. It supports bounded inspection, exact cell patches, a deterministic two-or-three-rectangle agent plan, SVG footprint preview, revisions, actor grants, commit-time protection and lock checks, atomic transactions, undo, and ordinary Tiled JSON export. Same-ID sparse patches must preserve previously owned untouched cells, terrain, elevations, ID, and metadata; cells merely inside the bounding rectangle remain untouched. Authored nonblank base cells and cells owned by other region IDs cannot be overwritten. Its preview is not the final 3D scene. The experiment does not have generalized entity placement, arbitrary asset semantics, Godot export, book or image interpretation, behavior authoring, networked games, or training data. Inspect the exact branch and rerun tests before treating this snapshot as current.

There is also an isolated experimental Qt desktop shell with a selected-map watcher; its Map tab is a placeholder. It neither replaces the browser-first target nor proves native Tiled integration. SUBSTRATE and FrameChute have their own existing workspace/frame work and proposals; no cross-repository world integration is implied merely because these documents appear in all three repos.

## 4. Seven stages, one creator journey

These stages express **capabilities to prove**, rather than seven compulsory apps. Stages 1–3 make the world; Stage 4 places existing and newly generated objects; Stages 5–7 create assets that return to Stage 4. Each stage keeps an easy default and a precise path for people who want more control.

### Stage 01 — ÆXIS: establish the world

**Creator action:** Open or import a map, or start with sensible defaults. **World contract:** stable IDs and revisions; canonical map X → world X, map Y → world Z, elevation → world Y; units, topology, transforms, terrain types, ownership, layers, source provenance, scale, and editable local regions. Preserve Tiled data and source elevations. Store logical oceans implicitly when using larger master extents. A two-main-landmass, three-small-island, dispersed oceanic world is a useful *default brief*, not a universal rule: counts, clustering, island classes, minimum sea, and land coverage must be adjustable. A 500 × 500 demonstration can cap each main landmass at roughly one quarter of the area as an authoring default, without making that an invariant for all worlds. Distinguish small/medium islands, large landmasses, continents, floating geography, and user-drawn shapes by explicit extent and semantic relationships. **Proof:** reopen and export the same geography and IDs; agents can locate and inspect a region without inspecting pixels.

### Stage 02 — AERIS: inhabit the sky and ocean

**Creator action:** Enter the world and fly as a lightweight ship; a later person/avatar mode can transition from flight to landing and walking. **World contract:** ocean and sky remain visually distinct; navigable altitude, terrain-aware descent, collision, horizon, scale profiles, and usable atmosphere reference the same geography. A large sea can be represented through a master extent and sparse land placements, drawing only bounded visible water; distinguish area multiplier from travel-distance multiplier. World navigation topology must be declared. If the user reaches an edge, repeated flat-map coordinates may meet across it; a true sphere or new firmament is a separate later adapter with its own polar and seam behavior. Distant proxies must resolve to the same landmass on approach. Offer appealing sun/moon/sky defaults, later editable multiple moons, clock/path, haze, cloud filtering and low-cost lighting fallbacks. **Proof:** flight, crossing and save/reentry use the same terrain truth; frame time and memory are measured on the target device.

### Stage 03 — EARTH (formerly TOPOS): geography with usable surfaces

**Creator action:** Draw or import local maps, preview a terrain interpretation, then apply or adjust. Tiled shapes such as lines, rectangles, ellipses, quads and polygons can encode desired or exact boundaries. **World contract:** a tunable **Within Reason** constraint engine separates hard facts (protected cells, coast continuity, valid heights, minimum spacing) from soft priors (plausible ridges, curved shores, slopes, varied mountain profiles). A mountain is a named landform with connected base, summit/ridge structure, coherent gradient and range constraints, not one random height spike or one universally fixed ceiling. Let deliberate fantasy geometry opt out of ordinary priors. Use seeded local generation; move an entire landmass by changing its master transform without erasing its local authored map. Publish a stable surface ID, transform, bounds, footprint, height/normal, ground/floating status, clearance, occupancy, protection, and relation to the terrain beneath. **Proof:** import a small authored region into a larger world; preserve original cells/elevation; inspect why a proposed change conflicts; reimport and undo without loss; place a simple object on a valid surface.

### Stage 04 — SEKAI: assemble the world

**Creator action:** Upload/select a GLB, click a compatible spot, preview, and drop; move or remove it later. A plain contact plane is sufficient at first; a floating circle, hillside, mountain, or island support may be offered as a later choice. **World contract:** one canonical object ID shared by the model, a non-destructive Tiled footprint marker, renderer proxy, collision/occupancy, anchor, placement surface, and source asset. A Blender-friendly labeling interface begins with entire objects, named nodes, points, and simple quad surface patches (`base`, `door`, `grip`, `walkable`, `attachment`), then extends to polygon sets and volumetric segmentation. Store the asset hash, axes/units, local anchor, normal, provenance and unresolved rebind conflicts after mesh replacement. Place by actual contact, clearance and author constraints; let an agent propose the same operation and receive the same diagnostics. **Proof:** import a real GLB, label base and door, place, save/reopen, Tiled/3D inspect, move/undo, and use a tested Godot starter-scene adapter for the supported subset. No claim that ordinary GLB alone contains all ÆXIS semantics.

### Stage 05 — ASTRA: create ships and reusable construction tools

**Creator action:** Describe a ship, provide optional sketches or several angles, choose Default, Detail or MINUTIA, refine locally, then place via SEKAI. **World contract:** an editable part tree, measured parameters, attachments, materials, provenance for observed versus inferred parts, inspect-render-compare-revise cycle, versioned export to GLB plus semantic record. This is the first application of a general construction kernel. Preserve an attractive inexpensive first draft, then allow inspection of pipes, structure, cockpit and engines when requested; unseen internals remain labeled inference. Ships can accept user-created flight and docking animations. **Proof:** create and revise one unfamiliar silhouette while preserving part IDs and working world placement; do not pass off a fixed template as free-form reconstruction.

### Stage 06 — ARCADIA: build architecture from the same kernel

**Creator action:** Describe/show a building, inspect its rooms and outside, refine, and place it. **World contract:** foundations, floors, doors, stairs, interior/exterior correspondence, route and support semantics, passage clearance, optional furnishing and electrical detail. Houses, towns and monumental structures reuse Stage 5's geometry/revision machinery with architectural rules, rather than a disconnected generator. **Proof:** an editable building's entry, floors, and contact surface remain coherent across model revision, placement, and a runtime adapter.

### Stage 07 — ANIMA: build inhabitants and expressive form

**Creator action:** Describe/show a character, adjust shape, face, clothing, expression, rig and actions, then inhabit the world. **World contract:** shared semantic body roles, deformable proportions, special skull/face morphologies for humans and anthropomorphic characters, attachment/contact, appearance and motion as related yet separable representations. A character can have a paper-flat image and a 3D embodiment with **one identity**, inventory and health. Rigging and model-created motion are progressive capabilities, not a prerequisite for a useful placed character. **Proof:** create, edit, and place an original character; transfer a scripted reach/grab to a second reshaped rig using semantic landmarks and report calibration failures.

## 5. The shared semantic engine beneath the stages

Model a versioned **world, spaces, regions, surfaces, entities, components, relationships, time, events, actions, permissions, and provenance**. Keep render meshes, Tiled cells, GLB nodes, source documents and Godot scenes as typed projections or assets bound to canonical IDs. Define bounded queries (`world/region/surface/entity/asset/action.inspect`, `relation.query`, `changes.since`), machine-readable capability/schema discovery, and exact errors. A small illustrated or SVG preview can explain an operation without launching a full renderer. Every operation carries actor, scope, operation ID, expected revision, affected IDs and cells, seed if relevant, source attribution and a reviewable diff. Commit validates permissions, locks, collisions, authored cells, schema and resource bounds again, even for hand-built operations; either everything persists or nothing does. Undo and exported round trips preserve identities and untouched information.

Separate **what is true** (coordinates, topology, supports, hits, ownership, cost and temporal state) from **how it looks** (curved horizon, paper shading, sprites, 3D mesh, film camera, VFX). A flat repeated world is not mathematically spherical. Multiple world/medium adapters can share truth without guaranteeing every engine supports every feature. Record losses and unknown extension data explicitly on import/export. A Godot handoff should include a demonstrable scene, placed GLBs, terrain/height subset, stable IDs, semantic sidecar, units and an unsupported-feature manifest. An agent can use its spatial footholds to implement a game with less screen-reading guesswork; no API guarantees that any request becomes a good game automatically.

Give precise diagnostics without making the everyday workflow a debugger. Ordinary errors identify the object, violated rule and suggested correction. Deep debug optionally shows transforms, surface normals, contact volumes, spatial queries, render projection, load, and provenance. Capture possible evaluation/training pairs only with creator permission and appropriate rights; do not treat private books, artworks or feedback as automatically reusable training material.

## 6. Toonworld, image interpretation, action and spectacle

The proposed **Toonworld Dynamics** research couples one deformable 3D rig to separate, hand-drawn 2D views. Each front, side, back and three-quarter view has its **own** artwork, camera pose, visible-part polygons and semantic links (`left_hand`, `jaw`, `torso`) to shared rig controls. Record occlusion, silhouette and intentional stylization rather than forcing the picture to be a literal projection. An artist can shift a rig or cage to match that drawing; one angle never uniquely specifies the hidden body. Compare projected bones/body to labeled drawing edges, fit candidate shapes, and let the artist correct them. Train or evaluate on consented aligned examples, including distinct characters and camera angles, without asserting that a particular dataset size solves the problem. The goal is eventually to see an unfamiliar cartoon and propose an editable skeleton, 3D body and angle-aware drawn rendition. Start with scripted, artist-approved examples; validate held-out shapes and usable grabs before learned special moves.

A suggested playable demonstration begins as an old-timey drawn 2.5D belt-scrolling action game. In a special move the paper character tears open, its X-eyed drawing falls to the ground, and its rigged body emerges into the already-existing 3D stage for an interactive fight or grab; it later picks up the drawing and returns. The flat drawing is a return prop, not a second player entity. The same character state, collision, camera intent and action rights survive both views. Camera-aware compositing decides which drawn hand is in front of a grabbed 3D object, while actual contact uses the rig and world model. This is a demanding research/game milestone, **not** a current feature.

Later, a versioned action and behavior language could encode reach, grab, lift, throw, land, transform, animate, speak and respond through preconditions, time, contact, events and camera cues. A creator can lift a GLB or landmass and drop it in a new location with an optional animation or wave; the committed world operation and its cinematic visualization must agree. An LLM may author proposals for dialogue, manners, speech, attacks and variation, but deterministic constraints decide actual collisions, permissions and results. A low-cost client may see reduced effects while sharing the same authoritative outcome.

An eventual **creator battle** and live broadcast is one possible game built on those foundations: crossovers between creator-owned characters/styles, counterable cinematic moves, a spectator camera/music timeline, fair match rules, recurring opt-in Nemesis rivals and transparent statistics. Existing event proposals sketch cash prizes ($5,000 per winning player, $2,000 for qualifying progress, and a possible $100,000 shared team prize for consecutive-year wins) and possible employment offers. These are **ideas requiring funding, published eligibility and actual hiring terms**; no current tournament, prizes, or job program is promised. Build small offline combat, replays, and validation before any networked or paid event.

## 7. From an author's book to a world: the complete intended workflow

1. **Bring material:** a Tiled master or several local maps, book or paragraph, overhead and side pictures with notes, existing assets or none. Track authorship, license and which details came from each source. Avoid assuming a public or recognizable franchise is free to reproduce.
2. **Interpret and propose:** extract named places, number and size of landmasses, relative distances, biomes, height clues, style, characters and ambiguities. Mark observed facts versus guesses. Let the artist ask for a different number of islands, ocean width, clustering or elevations.
3. **Make the quick draft:** generate a sparse master layout, individually editable local terrain, plausible seeded coast and ridge ranges, cheap 3D preview and a beautiful default sky. Use implicit ocean for vast spaces; ocean extent does not require storing one tile per meter. Keep consistent scale and seam behavior when wrapping.
4. **Correct locally:** move a whole landmass, sculpt one slope, redraw one coast, label a model's base, change a moon, or reject one incorrect inference. Show before/after and preserve locked and unrelated work. Make lifting/moving playful where the hardware permits; retain a precise numerical route too.
5. **Populate and enact:** import Blender GLBs or generate reusable semantic ships/buildings/characters, place via SEKAI, compose camera-aware 2D/3D effects, add actions and eventually game behaviors. Provide low-cost alternatives when full preview or inference exceeds the device.
6. **Deliver and continue:** save the canonical project and original references, export supported Tiled/GLB/Godot/browser representations with an explicit loss report, reopen, script or ask an agent for another change. As models improve, old projects remain editable through versioned migrations, not a rewrite of their meaning.

## 8. Ordered proofs and adoption strategy

These are **relative development gates**, not release promises or claims about staffing. Solve and measure each gate before broadening its scope.

| Gate | Demonstration and acceptance | Why creators would care |
| --- | --- | --- |
| 0. Reliability | Audit current browser flow and v1 API; tests/build/500 × 500 smoke pass; capability manifest describes only implemented operations; protected and locked edits fail atomically. | Trust the first tool with authored maps. |
| 1. Tiled delight | Import a stranger's ordinary supported Tiled map and supplied elevations; show attractive flyable terrain quickly, change one region, export/reopen/undo without losing unrelated cells or IDs. Give useful unsupported-format errors. | A Tiled maker sees their own world become explorable. |
| 2. Sparse world + surfaces | Several movable local maps, implicit sea, shape/height previews, coherent coastline, stable named support surfaces and bounded queries. | Big worlds without vast empty ocean files. |
| 3. Blender asset loop | Import one real GLB, label base/door, preview/place/move/reload, reconcile a changed mesh; agent and programmer see identical IDs and conflict rules. | A Blender artist brings their work intact. |
| 4. Godot bridge | Export one documented supported world subset into a runnable Godot sample with exact transforms, metadata and losses. | Existing game projects can adopt the workflow. |
| 5. Browser game slice | One playable interaction with deterministic actions, one animated character, input/collision, save/replay and low-cost visuals. | A prototype can grow into a real game. |
| 6. Multimodal authorship | A rights-cleared authored brief plus several pictures produces cited, editable geography and asset proposals; test on held-out briefs and record correction cost. | The author's intent drives assembly. |
| 7. Rich worlds and media | Selective advanced generation, Toonworld multi-view rigor, editable sky, open style rules, games, speech/behavior integrations and optional broadcast/event systems, each with its own proofs. | The expansive creative vision becomes sustainable. |

An early public invitation should remain simple: **“Bring your Tiled map. See it as a beautiful, editable world. Change it yourself or with an agent, and keep your work.”** Follow with a beginner GLB path, Blender guide, and tested Godot example. Offer a demo with no compulsory AI account, one short walkthrough, open formats, undo, helpful diagnostics and rapid feedback from Tiled/Blender/Godot creators. Measure time to first own-map preview, first accepted edit, saved round-trip fidelity, successful repeat use and clear failures; do not use proposal counts as proof of adoption. Godot's mature engine, GDevelop's creator experience, PlayCanvas's browser editor and agent access, and specialized 3D generation/asset tools already set a high bar. Differentiate through the complete trustworthy authoring loop and the creator's delight.

Treat a **4 GB RAM Windows computer with integrated graphics** as the first real performance target for bounded editing and small-world preview; profile startup, peak JS heap/GPU memory when measurable, import/preview/commit latency, frame time, recovery and export. Derive numerical budgets from actual hardware measurements. Use chunks, instancing, LOD, lazy loading, cache limits, low-cost sky/ocean, proxy assets and quality controls. Preserve source quality while reducing displayed detail. Optional remote inference/rendering should never become a requirement for basic map inspection and editing.
