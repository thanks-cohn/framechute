# TOPOS Stage 3 → Stage 4 — Shape-Aware Tiled Geography, Universal Placement Surfaces, and GLB Footprint Synchronization

**Status:** Proposal only; implementation is not claimed. **Date:** 2026-09-23.  
**Roadmap:** ÆRIS Stage 2 = lightweight cinematic flight and multiscale rendering; TOPOS Stage 3 = robust geography import/edit/renderer contract; TOPOS Stage 4 = place GLB assets in 3D and create matching editable Tiled + world-JSON object representations. Keep the user-facing path simple: **import → detect changes → Default or Customize → preview → apply**. Agent/advanced options exist but are not mandatory.

## 1. Product promise and what Stage 3 MUST finish

The creator edits the large Tiled world by adding little authored maps, painting terrain and drawing optional shapes. TOPOS imports the new map and compares it with the **previous Tiled revision AND the existing generated world-state JSON**. It identifies what changed and which new or edited cells/regions lack elevations, material metadata, surface relationships or render-ready placement information. Do not invent that a missing elevation of 0 is an authored zero: distinguish *missing* from *explicitly flat*.

For each unresolved group, show a compact card: “New region at map (X,Z), approximately W × H tiles. Elevation missing. **Create default** / **Customize**.” Infer safe defaults from the existing neighboring semantic tiles and region connections, but show assumptions. A one-click Default makes ground-level, low-relief traversable terrain when the shape's semantics permit it; if conflicting authorship, overlapping geometry, ambiguous underneath, unknown tiles or genuine missing links matter, ask just the question required. An advanced section can offer exact elevations/constraints. Show the preview before writing. Do not regenerate the whole planet or overwrite protected imported maps for a small edit.

**Stage 3 acceptance:** A newly added/modified Tiled region can be compared, validated, generated into the same authoritative geographical representation used by flight/rendering, and made ready for later object attachment, with coordinates, stable IDs, surfaces and known/unknown semantics. It does not yet require arbitrary user-GLB placement.

## 2. Where shapes are drawn: Tiled first, optional browser editor second

Tiled already has **Object Layers** with rectangles (including quadrilaterals represented as polygons), ellipses/circles, arbitrary polygons, polylines and points; objects can be named and have custom properties/classes. Preserve actual Tiled JSON object data and use those features directly, not pretend that the tile-layer pixel art itself encodes a polygon. Source documentation: https://doc.mapeditor.org/en/latest/manual/layers/ and https://doc.mapeditor.org/en/latest/reference/json-map-format/ .

Normal creator route: add a Tiled **TOPOS Shapes** object layer; draw a line, quadrilateral, rectangle, polygon or ellipse/circle around/through new maps, give it a simple meaning via a class/property or select meaning after import. Tiled's JSON stores rectangles via x/y/width/height (optionally rotation), ellipses via `ellipse:true` and bounds, polygons/polylines as **points relative to their parent object position**, and pixels rather than tiles for most ordinary maps. Use map tilewidth/tileheight, map orientation and layer offset/rotation when converting; do not equate raw object X/Y pixels with tile X/Z coordinates. Preserve original object IDs plus a stable TOPOS ID and source revision; handle isometric and unsupported cases via explicit adapter/error rather than silent coordinate guesses. A quadrilateral is a four-point polygon, not a magical distinct Tiled type.

Optional alternative: after importing, provide a tiny **Add shape** browser overlay with Line/Polyline, Rectangle/Quadrilateral, Ellipse/Circle and Free Polygon tools, snap/undo and a live footprint readout; allow direct editing of the same semantic shape records and export back to a compatible Tiled object layer. Do not require creators to draw things twice or make the browser editor a prerequisite. A creator can import an already-shaped Tiled map and simply answer semantic questions. Browser drawing must not infer authoritative world positions directly from viewport pixels: raycast/projection into a named surface, then resolve map-local coordinates through the Stage 3 coordinate adapter.

Shape meaning is not shape type. Offer `Make landmass`, `Keep ocean`, `River`, `Road`, `Coastline`, `Ridge`, `Plateau`, `Floating island`, `Reserved buildable surface`, `Protected authored region`, `Passage/opening`. For polyline, ask width/corridor and whether it is a centerline, boundary, connection or watercourse; a zero-width line is not a usable landmass. For enclosed shapes, **Desired area (approximate, default)** versus **Exact boundary**; generated coastlines may vary only within declared tolerance for the first, and must respect a true hard boundary for the second. Circles and rectangles are envelopes by default, *not forced circular or rectangular islands*. A non-axis-aligned quad is represented as a polygon with four vertices.

## 3. Default-first semantic questions

When the new map and shape data are sufficient, create the safe default and offer preview; otherwise group questions per changed region, never ask one question per tile.

- **Geography:** Ground-level landmass (default when appropriate), elevated terrain/plateau, floating island, water/lake/river, artificial platform, or preserve existing.
- **Outline:** Desired area / Exact boundary (plus optional tolerance, width for lines, smoothness, coastline transitions).
- **Height:** Default inferred ground surface; optional numeric world-unit elevation or relative offset and bounded slope/cliff/flatness; display scale-dependent safe input range derived from actual renderer/collision limits, not an invented universal `0…N` ceiling. Permit custom numeric heights only after validation.
- **Floating:** Height above a named local reference surface, support/visual underside preset (none, flat slab, tapered rock, inverted mountain, aesthetic cliff, custom future GLB); top surface and underside are distinct; optional movement. The **initial default surface MUST ALREADY ACCEPT Stage 4 objects** even without any ornate underside. Do not promise one-click physically faithful rocks, cliffs or mountains now if those presets are not implemented.
- **Beneath:** Preserve existing ocean/ground by default; explicitly choose Ocean, Grassland, Rock, New landmass, Preserve unchanged, or a supported preset. A floating island NEVER overwrites the ground beneath by default. If a circle or polygon crosses existing authored structures, warn and preview.
- **Landing/placement:** Default object-ready top surface with a normal, elevation, clearance, usable contiguous area, occupancy grid and stable named surface ID. Separate “may place a prop” from “walkable” or “safe to land a spacecraft”; do not assume all objects can sit on every slope.
- **Conflicts:** Existing protected shapes and authored local maps win until the creator explicitly unlocks them. Show conflicts and offer alternatives instead of guessing or silently deleting source geography.

Examples: “Polygon X=240–290, Z=180–230 has no numeric height: **Default low island** / Customize → Elevated / Floating → height relative to underlying water → underside Flat / Rock (when supported) → beneath Preserve Ocean → Preview.” A creator who wants a plain floating plane chooses Floating, height and the **Flat/None** underside preset, then commits.

## 4. Import → compare → generate → commit, with an actual renderer API

Define a typed, versioned, engine-neutral **TOPOS World IR** instead of coupling Tiled to incidental renderer JavaScript data structures. The authoritative record includes:
`worldId`, revision/hash, map dimensions/tile metrics/orientation, source provenance, authoritative terrain/material IDs, numeric height fields *with missing-value mask*, protected anchor regions, stable region/surface/object IDs, region geometry (polygon/polyline/ellipse bounds/rect plus coordinates and rotation), per-surface height/normal/bounds/footprint/buildability/clearance, parent/child and under/over spatial relationships, generated seed and rules, object occupancy, asset references and renderer LOD hints. **World IR is the source of truth; JavaScript render modules are derived artifacts** where needed by the current runtime.

Proposed public operations (illustrative contracts, not existing functions):
`topos.importTiled({map,previousRevision,worldId})`;
`topos.diff({previousMap,currentMap,worldIR})`;
`topos.listUnresolved({revision})`;
`topos.planRegion({regionId,preset,outline,elevation,underneath,underside,placementPolicy})`;
`topos.previewPatch({revision,patch})`;
`topos.validatePatch({revision,patch})`;
`topos.commitPatch({expectedRevision,patch})`;
`topos.export({format:"tiled-json"|"world-json"|"js-module"})`;
`topos.querySurface({worldId,point,mode:"placement"|"landing"})`.

The parser compares old/new tile IDs and semantics, elevation sidecar and missing mask, object-layer shape IDs/properties, local-map placement offsets, map dimensions, and generated IR. Do not assume Tiled's sequential numeric object IDs remain globally unique across independently imported submaps: namespace by source map + local ID and preserve a stable semantic ID across reimports. Detect source revision conflicts; surface clear added/edited/deleted changes and ask whether to preserve prior hand-authored heights when a tile's color/material changed.

Generate only affected terrain chunks and seams; update near-field geometry, surface/collision query adapters and overview map from the same IR. **Do not eval uploaded scripts, execute Tiled properties as code or trust arbitrary file paths.** Stage 3 may export safe derived .js or a generated JSON consumed by the browser, but generated JS is not the only truth. Never silently replace authored files; generate a preview and an atomic explicit save/download or compatible Tiled-editor patch. Keep user edits and generated layers separate, reversible, with provenance. Keep world-size memory independent of total 16,000 × 16,000 coordinates through sparse chunks and stable seeds.

### Surface contract — Stage 3's most important promise to Stage 4

Every accepted geographical region should expose a **queryable placement surface**: stable `surfaceId`, `worldId`, parent region ID, canonical X/Z domain and world transform, `heightAt(x,z)` or explicit plane/collider, surface normal/slope, material, ground-vs-floating type, bounds and elevation range, allowed object footprint types, occupancy/conflict map, minimum clearance and underlying-surface relationship. It is a *surface adapter*, not a requirement for one physical mesh per map cell. Default-generated ground and floating plane both implement it. An arbitrary imported top mesh must declare or derive a safe placement surface rather than pretending all GLBs are planar/walkable. Expose exact world↔map tile transforms including scale, Y/elevation and parent offsets, and explicit unknowns.

Stage 4 must not need to write special-case placement code for every Stage 3 region: `querySurface` / `previewPlacement` / `commitPlacement` operate on the same contract whether the target is sea-level ground, a simple raised area, or the flat top of a floating island. Preserve the geography **under** floating objects and islands independently; no one-value-per-X/Z flattening.

## 5. TOPOS Stage 4 V0 — right-click, choose asset, place, mark footprint

Stage 4 begins with the *simple working workflow*, not photoreal image-to-sprite inference:

1. Open the rendered world, right-click a valid position and choose **Place asset**. The engine raycasts or spatially queries the clicked surface; display X/Z/Y, host surface ID, and basic occupancy/slope conflicts. A floating aesthetic circle is a selectable *placement preview/marker* (or choose Flat Plane), not a mysterious new island that changes physics by default.
2. Pick a GLB from a known local asset library/dropdown, or **Upload GLB from computer** into the user's authorized local project. Support choosing a predetermined destination or the currently clicked position. Show a safe preview with default north/east/south/west forward-axis orientation, unit/scale, rotation, bounding box and ground contact/pivot adjustment. Do not automatically execute code from untrusted assets. For the minimal V0, accept an existing GLB and a simple placeholder when absent; later photo-to-pixel-art conversion is independent.
3. Choose **On ground / Elevated / Floating**; if floating, show height above named supporting surface plus optional underside `None / Flat plane` now; future `Mountain / Hillside / Decorative cliff / custom GLB` may be offered only when implemented. **Make ground underneath** defaults to `Preserve existing`, with explicit optional generated ground material and footprint, always previewed separately. This must work whether the GLB is placed on an imported ground region, a Stage 3 floating plane, or a new temporary plane created by the placement wizard.
4. Compute a conservative **top-down occupied footprint** of the transformed GLB (bounding box/collision footprint, scale, pivot and rotation), project it into canonical X/Z and map tile cells. Do not assume object height is its ground footprint or that the source thumbnail establishes true 3D bounds. For irregular shapes, mark intersected cells or a documented safe conservative rectangle; show exact covered tile count and allow padding/resizing. Check existing occupancy/collision and protected authoring zones.
5. **V0 Tiled representation:** on a dedicated named overlay layer, paint/assign reusable **WHITE TILES WITH AN X** to each covered footprint cell, including white padding cells where necessary to fully cover the projected footprint. Keep original terrain and elevation layers intact: the marker depicts occupancy/selection, not grass/water replacement or a magically finished RPG sprite. For a floating object, preserve separate elevation/host-surface metadata (tile X/Z alone is insufficient). Include a simple anchor marker and same semantic object ID linking to the 3D instance.
6. In one version-checked reversible placement transaction, update **both** the editable Tiled map/export (tile overlay + object metadata) and the canonical `world.json`/generated render `js` representation (asset ID/path, transform, host surface, bounding/occupied cells, elevation/underneath, interaction placeholder and provenance). If writing directly back into the currently opened native Tiled file isn't supported by the environment, export a validated updated Tiled JSON (or Tiled plugin-applied patch) and matching world JSON together; **never claim both files changed unless both were successfully written**. Prevent partial commits and duplicate placement on reimport.
7. Let the player see the placed GLB in the browser and see the matching white-X footprint when the Tiled map is reopened or exported; moving/rotating/deleting it later updates both representations deterministically. On missing textures/invalid geometry or map-conflict failure, keep previous map/world state intact and show actionable feedback.

**Stage 4 V0 is deliberately NOT the final pixel-art pipeline.** White X tiles are the first inexpensive, unambiguous spatial placeholder. A later Stage 4 refinement imports an accompanying picture, generates transparency/white surrounding padding, turns it into proportionate styled pixel art and writes the correct 2D RPG tile/sprite representation **without changing the existing footprint ID, position, 3D asset, host surface or the geometry/collision truth**. Nonrectangular or multiple-floor geometry needs an explicit later occupancy model, not an inference from a pretty picture.

## 6. Agent-first observability, safe ownership and light-resource rules

Agent-facing `topos.inspectRegion(id)`, `topos.inspectSurface(id)`, `topos.inspectAsset(id)`, `topos.explainDiff(revisionA,revisionB)`, `topos.getPlacementPreview(...)` should return both authoritative world coordinates and projected viewport coords **with source/units**, not screen guesses. Deep Debug may show shape vertices, missing-elevation cells, height/normal samples, named underlying surface, contact transform, marker cells, revision/asset provenance and exactly why a patch was proposed. Authorized agents and humans use the same versioned API; edit permissions are scoped to this world and require an explicit approval/commit. Performance mode does not trace every tile or per-crest object each frame.

Preserve Stage 2's cinematic ocean, shadows, clouds, camera and ship momentum. New terrain/objects should be chunk-streamed/LOD controlled; do not create individual draw calls per tile, allocate a 16k² map, or regenerate the whole planet when adding one GLB. Distinguish editor-preview geometry from normal flight geometry; pool/dispose previews, load GLBs on demand and use simple distant proxies. Every action must be possible offline without a mandatory LLM.

## 7. Stage gates and concrete end-to-end acceptance

**Stage 3 test:** Modify an existing large-world Tiled map by adding a protected 50 × 50 local map and drawn line, polygon, rotated quadrilateral and ellipse. Import again; diff reports true new/edited regions. Use Default on one and Customize floating+numeric height+preserve ocean underneath on another; preview shows distinct upper/lower surfaces; commit generates valid Tiled + IR/renderer update without changing unrelated islands/heights; one click/surface query returns a legal object-ready surface with correct 2D↔3D coordinates. Reimport yields no duplicate regions or false elevation-missing alerts. Tests cover pixel/tile conversion, object rotation, polygon point offsets, shore holes, overlap precedence, wraps, scale, missing-vs-zero heights, low-memory sparse sampling and rollback.

**Stage 4 V0 test:** Right-click the generated surface, choose an uploaded library GLB, rotate/scale it and optionally make a floating plane with existing ocean underneath. Preview safe contact and footprint; commit displays the GLB and a same-ID overlay of white X tiles covering exactly/conservatively the occupied cells. Reopen the exported map in Tiled and load the paired world JSON/derived JS: both represent the *same* asset at the *same* placement, orientation, height, host surface and revision. Changing or deleting the asset reversibly updates both. Test two assets on one surface, footprint conflicts, cross-tile rotation, separate stacked surfaces, missing file, invalid map and interrupted save. Verify actual browser appearance and 4 GB device performance separately from unit tests.

**Scope control:** Deliver Stage 3 first as an actual tested engine/API implementation when development is authorized; then Stage 4 V0 placement and X-tile occupancy; then picture-to-pixel-art, advanced undersides and interactive interiors in later increments. This document is a proposal, not a claim that code works. Keep proposed options disabled or clearly marked future until their implementation exists.

## FrameChute integration scope

FrameChute hosts an optional world/editor frame; it must not convert ordinary PDFs/docs/website frames into unrestricted game render surfaces. Expose a permission-scoped bridge from the frame to TOPOS World IR and the versioned import/diff/preview/commit API, with real source-revision and undo support. A user may still author in external Tiled and import JSON; Stage 4 asset library and GLB upload choices must be scoped to that world/project, not to every browser tab. Keep runtime browser editing lightweight and preserve file/frame permissions.
