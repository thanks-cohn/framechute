# Saeki — In-World Block Editing and Tiled Round Trip

**Status:** Proposal and inspected implementation plan; no block editor, Electron shell, or block round trip is shipped.  
**Date:** 2026-09-24  
**Applies to:** Tiled-223D, SUBSTRATE, and FrameChute.  
**Related:** `Stages/README.md` (EARTH and placement surfaces), `Proposals/aexis-shape-aware-map-insertion-stage-4-glb-placement.md`.

## The experience

Import or assemble a Tiled world, enter it in Chrome or a Chromium-based Electron desktop shell, and build directly in the scene: select a material, point at a face, place a block on that face, stack upward, delete, repaint, undo, and save. Saving writes a **new editable Tiled JSON map** and a versioned world record; importing those outputs reconstructs the exact authored blocks. Tiled remains useful for overhead planning, while Saeki permits sculpting from inside the world. The initial generator remains simple: infer a plausible ground height and color from terrain semantics, then let the creator refine the result. A generated preview never overwrites manual work.

This is a proposal for an editor and reversible data interchange, not a claim of Minecraft-scale simulation, destructible terrain, general browser extension compatibility in Electron, or a shipped Electron app. The browser world must remain independently runnable in Chrome; Electron provides local project file access through a narrow bridge.

The existing surface mesh does not encode a cavity, bridge, overhang or several independent blocks at one X/Z coordinate. This calls for a **new editable block layer and collision path**, while retaining the flight scene, atmosphere, camera and existing heightmap for non-block terrain. It is a substantial additive renderer change, not a rewrite of the whole world.

## Canonical model and coordinates

- Preserve Tiled `(column,row)` as world `(X,Z)` and use **world Y as vertical**. Block grid key `(x,z,level)` uses integer x/z/level and a documented `blockHeightWorldUnits`; `level=0` has an explicit world-space datum. Do not confuse a 32-pixel tile, one horizontal world unit and one vertical elevation unit.
- Keep `Ground` terrain semantics and numeric elevation authoritative for the original smooth terrain. Store **authored blocks independently** as a sparse map of occupied 3D cells, each with material/semantic ID, source/provenance, protection flag and optional per-block metadata. Empty space is explicit absence; water is a separate semantic and is not implicitly a solid block.
- Choose a surface-to-block transition rule before implementing excavation: initial MVP may allow placement above and beside the height surface, with removal restricted to placed blocks. A later **Convert region to editable blocks** operation must snapshot the selected original surface and protect untouched neighboring cells. Never pretend deleting a rendered terrain triangle is the same as removing a stored block.
- For a newly generated map, take a saved generation seed and simple semantic color/material palette as the starting geometry. Preserve authored top color and ground-level assumptions. Distinguish inferred blocks from hand edits so regeneration can touch only its own cells.
- Give the project a stable `worldId`, map revision, block schema version, coordinate/units declaration, tileset references and provenance. Keep authored terrain, shape/GLB records and future layers alongside blocks; exporting must not erase `Additions`, `WorldShapes`, `AssetFootprints`, spawns or unknown safe map properties.

## Tiled interchange

Use one Tiled-compatible, uncompressed orthogonal tile layer **per occupied block level** (`Blocks Z=0`, `Blocks Z=1`, etc. may be convenient labels, but call the vertical coordinate `Y` in schema metadata to prevent confusion with world Z). Prefer `Blocks Y=0` names with an explicit integer `blockLevel` layer property. A cell's tile GID identifies block material by a real referenced tileset, not by its display color or a hard-coded global GID. Zero means no authored block. Preserve Tiled flip bits where meaningful or explicitly reject unsupported flips. Validate dimension, level, cell count, tileset, GID and bounds on import.

An optional project-side world JSON can hold metadata Tiled layers cannot express cleanly: coordinate units, generator seed, source/protection masks, material definitions, edit provenance and future object links. Define which fields are canonical and how a revision conflict is resolved. The **block occupancy and material must survive from Tiled alone** when exporting the Tiled map; do not require a private sidecar to reconstruct the visible block structure. Preserve exact authored numeric heights in embedded `substrateElevation` and/or a named elevation companion, with a documented precedence rule. Use an adapter for the existing `.sworld.json` exporter instead of assuming its schema matches `fromTiled()`.

When saving, write a new map revision or explicit save-as target, validate it by reimporting, and only then offer replacement of the original. In Electron, use atomic temporary-file then rename for local project writes; in Chrome, provide downloadable Tiled JSON plus any required companion. Asset references must be portable. Empty block layers may be omitted if that does not change the project identity. Do not flatten every vertical cell into the `Ground` layer or encode height only as color.

## In-world editing interaction

Enter **Edit World** from a safe, paused or slow-movement state. A crosshair/ray hits a block face or ground placement surface and shows a translucent preview cell, its world coordinates and material. Primary action places one block in adjacent empty space; secondary action removes a selected authored block; pick material and paint/repaint are separate actions. Provide keyboard and pointer alternatives, explicit edit/build versus flight mode, selection outline, a height readout, undo/redo and save status. Reject edits outside map bounds, collisions with protected ground, occupied object footprints or the player, and unsupported Y ranges with clear feedback. A user can make a floating block deliberately; support/physics must not silently fabricate a column underneath it.

An edit transaction updates the sparse block store first, then affected chunk geometry, spatial picking, navigation/collision and minimap/overhead representation. Group drag/brush edits into one undo step; autosave a recoverable draft where possible. A saved manual block is locked from terrain regeneration unless the creator explicitly selects it for replacement. Later tool modes may offer box fill, line, region selection, replace material, copy/paste and agent-directed edits through the same validated commands.

## Rendering and performance

Keep the existing smooth terrain renderer for the initial maps. Render blocks in **bounded chunks** with shared materials, exposed faces only, and local rebuilds or instanced visible blocks after benchmarking. Avoid one draw call and one physics object per cube; changing a boundary block dirties its chunk and neighboring chunk faces. Pick against the editable occupancy grid with ray traversal or an equivalent bounded method. Ground/ship collision must query block volumes as well as the original terrain; distinguish walkable tops, side hits, enclosed cells and non-solid water. Account for wrap at X/Z seams in picking, chunk updates and duplicate visual presentation, without mutating canonical coordinates.

Electron is an **optional shell around the same web renderer and core model**. Expose a narrow `openProject`, `saveProject`, `chooseAsset` bridge from a sandboxed, context-isolated renderer to its desktop process. Do not turn on Node integration for imported/remote pages. Test the web renderer in actual Chrome, desktop IO in Electron, and Chrome extension features separately. Preserve the 4 GB Windows integrated-graphics priority: measure cold startup, peak process/JS/GPU memory where available, p50/p95 frame time while moving and editing, edit-to-visible latency, save/reimport time and project size for a 500 × 500 map with a sparse 50 × 50 edited area. Set pass thresholds only after recording the baseline on the actual target; start with a target of at least 30 fps in low quality, under 100 ms for a single-block visible edit and no out-of-memory/frozen save, and label them proposed until measured.

## Ordered implementation gates

1. **Schema and round trip:** write examples and pure validation for block coordinates, materials, levels, Tiled GIDs, elevation precedence and versioning. Import existing maps unchanged. Add Tiled layer export/import and a `map → world → map → world` structural equality check across stacked, floating, deleted and boundary cells. Resolve the current `.sworld.json`/viewer mismatch explicitly.
2. **Sparse renderer:** add a separate chunked block layer above the current height surface. Render stacked blocks, a bridge and an overhang; changing one block updates only impacted chunks. Verify that imported old worlds retain their appearance and flight behavior.
3. **Editor transactions:** add face picking, place/remove/repaint, undo/redo, protection/conflict messages and collision updates. Save a draft without destroying input maps. Demonstrate an intentional unsupported floating block and a stable stack after reload.
4. **Tiled save/reimport:** write valid Tiled JSON with `Blocks Y=n` layers, tileset and metadata; reimport it to the same block positions and materials. Reopen in Tiled, add a layer/edit, reimport in the viewer and preserve existing non-block content.
5. **Desktop shell:** package the existing web editor as an Electron app with scoped project IO, then run the same world in Chrome. Keep optional desktop APIs behind an adapter. Integrate a SUBSTRATE/FrameChute launch/handoff only after its contract is tested; do not label any stage shipped from this proposal alone.
6. **Ground conversion and richer tools:** opt-in conversion of a bounded region to editable voxels, cave excavation, broad brushes, copy/paste and optional agent commands, all through the same persisted transaction model. Keep this distinct from the first playable stack-and-save release.

**First playable acceptance:** A creator imports a Tiled map, enters the world, places three blocks vertically, removes the middle one, adds a floating block and repaints another, saves a new Tiled map, opens that map in Tiled, reimports it in Chrome and Electron, and sees exactly the same occupancy/materials without altering protected original terrain or losing other map layers. Undo/redo and a failed save leave the prior revision recoverable. Record measured 4 GB Windows performance rather than asserting it.
