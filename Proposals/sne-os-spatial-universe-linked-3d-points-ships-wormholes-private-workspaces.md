# SNE:OS — Spatial Universe, Anchored Locations, Private Workspaces, Ships, Orbits & Liquid Wormholes

**Status:** Consolidated product and architecture proposal. This captures the current vision and sequencing; it does **not** claim that the proposed linking editor, three-world carousel, 3D flight, encrypted workspace packages, or Liquid wormholes have already been implemented.  
**Canonical product name:** **SNE:OS** (Simulated Neo Environments: Operating Space).  
**Development base:** FrameChute `sne-os-world-entry-v0`; mirror this proposal in the SUBSTRATE repository. Preserve the prior floating-island branch rather than backporting experimental changes into it.  
**Design intent:** Delightful everyday computing on modest hardware, with deeper authoring and navigational freedom for advanced users. The ordinary PDF/DOCX/frame/workspace core remains independent of the chosen game, world, transition, and navigation presentation.

## 1. The user-facing promise

“I like flying my little default ship, seeing its tiny animations, rediscovering my arrangements, and opening real files in places that I have made my own.” A SNE:OS world is not a fake file system: places, structures, doors, ships, schools, libraries, and hidden portals can link to actual authorized documents and workspaces. Spatial, visual, and emotional memory can make useful computing pleasant to revisit. The user may also choose immediate, ordinary access with no cinematic.

**Every visible world is a venue rather than the operating core.** The workspace/document system remains functional even if the GLB fails, the animation is skipped, a custom game breaks, or the user disables world mode. A destination may be accessible by more than one route, unless its owner deliberately configures an optional navigation-only route for a particular private space.

**Maximum control:** Users choose their assets, layouts, coordinate positions, linked destinations, lighting, motion, scripts, export contents, and access rules. Most users should configure common cases in Settings; advanced creators get an isolated Liquid Mode scripting surface. Do not hardcode today's starter island, UFO, town, animation, frame appearance, or model-specific mesh names into the permanent architecture.

## 2. True black underlying space; local worlds and ambience

The **real page/root/expandable workspace canvas and exposed scrollbar/overscroll areas** must default to `#000` in SNE:OS mode. Black is the substrate, **not a dark overlay that hides a white body or interferes with documents**. Keep classic canvas styling available when classic mode is explicitly selected. Validate actual horizontal/vertical scrolling, large expanded canvases, cold start, stalled GLB and WebGL failure in Chrome; a CSS test alone cannot prove a visually flash-free result.

An otherwise empty canvas/deep space is mathematically unbounded in intent and does not need an allocated grid, endless rendered 3D tiles, or an endless generated starfield. Maintain a ship/camera pose, sparse registered locations, and the transforms of nearby objects. The user may scroll arbitrarily in X/Y; the starfield, shooting stars and local ambient effects belong to a **bounded world/location zone**, not the entire viewport or infinite canvas. Leaving that zone reveals only the underlying black. Registering a location may spawn its own local starfield and ambience. Traversing empty coordinates does **not** register millions of saved locations; only a deliberate Dock/Create/Bookmark operation creates persistent records.

Depth (Z) is an additional navigational dimension reached through ship/3D navigation, while ordinary canvas mode continues to support X/Y. Coordinate records must be explicit about their reference frame: global canvas/universe XYZ, world-local XYZ, model-node-local XYZ, screen/viewport projection. For large distances, use camera-relative/floating-origin rendering while retaining stable canonical positions. Workspace and destination identity must not be derived solely from mutable coordinates.

## 3. Start with one world and a universal spatial-linking model

**This is the first substantive feature to prove, before adding three worlds.** Use the existing imported **Otherworld / The Last Stronghold** GLB and its Three.js raycasting geometry.

Right-click the world → **Linking** → **Add Linked Location**. The next selection of a 3D surface records an anchor attached to the selected eligible model/mesh or node. A visual editor asks for (a) point name, (b) optional human-language positional note such as “door,” “lake,” “house,” “upstairs dark door,” (c) destination type/ID, (d) optional presentation/transition, and (e) visibility/activation rules. Show the exact model and destination in **Linking → See Linked Locations**, with Locate, Edit, Test, Disable, Remove and later remap actions. In normal mode points can be invisible or appear on hover; edit mode reveals them. Multiple independent points can belong to a single fully rendered world.

**Anchor precedence and ownership, as specifically intended:** A placed 3D structure claims a protected *circular area projected into its desktop/canvas plane*. Its radius is conservatively computed from the structure's furthest exterior edge (a bounding sphere/projection plus configurable clearance), not just from the tiny mesh triangle under the cursor. While the user is in that object's occupied zone, object linking takes precedence **throughout the zone**: clicking a gap in its visible mesh must not accidentally create an underlying canvas point. On an exposed eligible surface, raycast to the nearest frontmost object. If the model or raycast geometry is still loading, do not silently bind to the canvas below. For overlapping occupied zones, choose the frontmost eligible owned object or require explicit disambiguation. Keep the ownership region and the actual 3D mesh/point intersection as distinct concepts.

**Deliberate concealment mechanic:** The user can create a global canvas location *before* placing an object at those coordinates. Later, placing/moving a structure over the location masks interaction with that preexisting canvas point. Moving the object away uncovers the original point without relocating or deleting it. The object owns clicks while present; it does not take permanent ownership of the hidden point's ID or data. This is a user-authored playful access mechanic, not encryption. Provide a deliberate object Move/Pick Up edit control and a saved way to find/manage the owner's own hidden locations. New global canvas points are created only on unoccupied canvas or by an explicit authorized editor action, **not** by ordinary raycast misses inside the object's zone.

Store stable IDs and local transforms so anchors follow world movement, rotation, scale, and, where supported, animated nodes. For genuinely deforming/skinned geometry, defer precise bone/surface attachment or offer an explicit stable surrogate anchor. Model replacement keeps destination records and asks for remapping of missing/changed anchor meshes rather than silently assigning a private workspace to a random new surface. Links and collision/alignment landmarks are different data types.

**Proof:** Create at least two separate 3D anchors on Otherworld, link one to the existing 2D town and one to an authorized workspace; create a global canvas point in unoccupied space; cover it with an object; verify it is inaccessible until the object moves. Rotate, zoom, restart, locate/edit/test all links, and verify they remain in place and their targets remain real. Only then introduce multi-world behavior.

## 4. Location registry and programmatic references

Each registered place has an immutable ID, name, universe XYZ (or relationship to a parent/orbital controller), optional world/asset and workspace IDs, optional visibility/access rules, dock pose, lighting/ambience configuration, linked points, and references to external files or private encrypted packages. An empty registered coordinate does not need a rendered model. The user may attach multiple entrances to a single destination, no visible entrances, a game passage, or a wormhole.

A future permissioned API should expose *descriptive* lookup and authorized operations such as `locations.find(id)`, `navigation.travelTo(locationId)`, `links.list(worldId)`, `worlds.place(assetId, coordinate)` and `navigation.dock()`. These are illustrative names, not already implemented methods. Stable IDs survive changing a model, re-spacing the carousel, updating its orbit, or restoring an exported workspace at a different position. Scripts reference IDs rather than brittle absolute file paths or hardcoded coordinates when possible.

Right-click on empty space or a world can expose context-appropriate options: **Dock** first when the ship is free-flying; Enter World; Create Location Here/Create Private Space Here; Linking → Add/See Linked Locations; See Locations/Travel to Location; World/Ship Settings. Object context menus must not steal PDF/DOCX/editor right-click actions. Keep the world-entry action name user-editable (default **Enter World**). The optional old vertical “World Key” remains off by default and restorable at the bottom of Settings for people who prefer explicit controls.

## 5. Three-world phase: curved carousel and faithful dark silhouettes

After linking is proven, import/register **three** example worlds, with the active detailed world in front and two dark background worlds to the left and right, at slightly different depths. Provide default consistent spacing; optional bounded, deterministic/seeded variation or advanced user-directed positions. Saved layouts should not unpredictably reshuffle on every launch.

Selecting another world moves it forward on a graceful, curved spline with subtle intentional vertical/sideways drift, not a straight-line conveyor or uncontrolled wobble. The old full-length starfield/shadow/slow-light reveal belongs only to first startup. Carousel selection uses its own short, premium movement/lighting transition with configurable duration/easing and reduced-motion/instant variants.

**Black coating ≠ performance optimization on its own.** Inactive worlds should use simplified cached **exterior silhouette proxy** meshes (or impostors when far away), no active high-detail material/texture/animation/simulation load. Far-off-screen worlds are location registry entries with *no renderer work*. Make fuller nearby/all-world rendering an opt-in profile for more capable computers, with actual GPU/VRAM budgets rather than assuming a black full-resolution GLB is cheap.

Each world owns one canonical origin and transform; proxy and full model retain matching model-local coordinates. During selection, begin loading/preparing the full GLB invisibly; keep the proxy dark and moving until the detailed model is ready; align bounding geometry, projected position, rotation and camera; switch representations **while both are still dark** using a controlled handoff that avoids opaque z-fighting; then reveal the selected detail with its configured light. If loading stalls, hold the dark silhouette/background without a white frame or sudden model jump. Never start a reveal merely because a timer elapsed. If independently imported proxy and full model differ, allow optional creator-defined matching landmarks to solve and check alignment; automatically generated same-source proxies should not need manual corresponding points.

Only one world needs full detail by default. The underlying documents/tasks are not automatically suspended merely because their scenery is inactive.

## 6. Invisible celestial light, ambient presentation and initial reveal

Default startup: underlying black → local stars gradually appear → occasional shooting stars → the ready model is visible as a fully dark silhouette at its final camera framing → a hidden light from the viewer's direction slowly lifts a dark coating while its illumination increases. **No automatic zoom/dolly or janky multi-step approach during startup.** If the model isn't ready, the independent local starfield remains the intentional loading state. Skip/retry and direct underlying workspace access remain available. Later optional anime-like glints, leaves/particles, sound and other visual enhancements belong to independent effect modules, not the first-stage minimum.

The initial celestial light is repositionable through Settings, invisible by default, and can begin on the camera/viewer side or any chosen user-defined bearing. By default it follows a complete collision-safe orbit around the selected world's bounding region, then transitions to cool moonlight; users can configure starting XYZ, safety clearance, duration, intensity/colors, sun/moon/other presets, multiple sources and optional visible celestial bodies later. Enforce the orbit's clearance around the **whole structure**, projecting unsafe start positions outward; freezing or changing an orbit triggers new safety checks. Imported unlit GLB materials must be adapted or have a compatible reveal material path if ordinary directional light would otherwise have no visual effect.

Every world has replaceable environment assets, light rigs, intro sequences, travel sequences and ambient effects, independent of its actual file/workspace destinations. One-click `Settings → Change 3D Background → choose compatible GLB → preview → apply` must eventually require no GitHub edit/rebuild; use standard GLB/glTF and portable, versioned JSON metadata. User-imported MP4/WebM or procedural 3D cutaways are route-specific, replaceable presentation rather than requirements to open files.

## 7. The little ship: travel, docking, depth and local creation

The **default ship** is meant to be fun to operate; keep the visible experience intuitive, while permitting advanced users to replace its GLB/model and configure behavior, trail, shaders, departure and arrival effects independently. Ship position (XYZ), orientation, motion/navigation mode, camera and dock state are separate from any document or location identity.

**Canvas mode** supports scrolling X/Y. **Free-flight mode** lets a user drag/steer the ship (arrow buttons or equivalent when flight controls are focused), tilt/pitch into Z, traverse black empty space, approach structures/orbits and hyperdrive toward a registered target or a chosen *empty* coordinate. Ordinary typing in a PDF/DOCX or text editor must never accidentally pilot the craft. Traveling through nothing is a cheap coordinate/camera update, not a mass terrain-generation process; do not automatically create saved locations while flying.

A directional scanner (bearing/depth/distance, not necessarily a literal sonar sweep) can guide an advanced navigator toward saved or orbiting places. Hyperdrive to a moving object should use its predicted position at arrival time if its orbit is deterministic. On reaching an empty destination, offer Dock, Create Location, Place Asset or Save Coordinates; stars and ambience remain absent until a location chooses them.

**Dock first in the flight-mode right-click menu.** Dock stops the ship, dims the engine, settles/parks it, and may display a tiny white landing ring. Docking does not *automatically* create a saved world: the user chooses to register that position after parking. When docked, desktop controls and document keyboard input behave normally. In future, customizable scripted docking can activate a landing pad, school, hangar or other venue.

## 8. Quick travel: useful menu actions feel delightful

Selecting Travel/Enter from a right-click menu can teleport the ship to the chosen registered place with a **default ≤1-second** optional effect: the ship gains a glowing white/liquid sheen, fine lines trace its contour, it leans/turns three-dimensionally toward the target, a brief trail/hyperspace streak appears, a thin white ring/line contracts or disappears, the target location comes forward, and its white coating wipes off **from the direction of approach**, revealing the prepared environment. Keep this sequence elegant and responsive, not a mandatory multi-second obstacle. The coating, lines, trail and arrival effect should work with any compatible uploaded ship/world asset rather than be hardcoded to the starter UFO.

Expose quick cinematic (default), instant (no delay), and manual pilot modes; allow disable, skip, reduced motion, animation duration, trail/ring/sheen toggles and safe fallback if a video/effect/model fails. Manual hyperdrive may last longer because users choose to pilot it. Destination lookup and underlying desktop access are independent of the visual flourish. Selecting a saved place may target a specific dock pose and appropriately light only that local active world.

## 9. Predictable, user-authored orbits and optional physical simulation

Advanced users can assign a world or other object an orbit around a point, another world, or invisible center; set initial position/phase, radius or ellipse/custom path, tilt, direction, speed/period and freeze/park state. Default paths can be safe simple circles; allow customization over time. Persist a reference epoch and deterministic orbital parameters so users can **chart/catalog/predict positions** at arbitrary times without simulating every preceding render frame. A separate orbital chart/timeline can list paths, nearest approach, conflicts, reachability and future position; scrub/freeze/resume the entire scene or a selected orbit.

Use conservative ownership/bounding spheres plus clearances to evaluate potential collisions over complete paths, not just at the initial position. Adjust/propose safe radius, speed/phase, path or parking location if necessary. Freezing one object while others continue may *introduce* a collision and requires replanning; Freeze All preserves separation at the frozen instant. Artistic wobble/tilt should not invalidate canonical navigation or collision envelopes. For scripted arbitrary paths, fall back to runtime proximity checks with clearly stated limits.

The default 4 GB-friendly profile can limit itself to sparse XYZ data, simplified nearby shapes and optional proximity warning (“WARNING — nearest location: …”). More capable computers may opt into dense environments, additional simultaneously detailed worlds, ship collision effects/physics and fuller simulations; these are elective resource-intensive features, not prerequisites for ordinary computing.

## 10. Private, hidden and portable spaces: owner chooses the rules

Private worlds can be placed at unseen canvas/depth coordinates, covered by movable objects, accessed from a special door/wormhole, or left without any visible entrance. Their storage and their visible location are independent. A workspace export preserves stable identity, canonical coordinates (or orbit/controller reference), local frame/object placements, anchors, destinations, layout and asset/file references. Offer:

- **Workspace Only:** lightweight metadata/reference package; on the *same computer and authorized SNE:OS profile*, reconnect existing persistent library assets, files and handles by ID/content hash/registered reference. Re-import at original coordinates or move/merge without changing internal IDs. If a source moved, permissions expired, or extension storage was wiped, request a relink rather than pretending recovery is guaranteed.
- **Workspace + Files:** self-contained selected documents, models, textures and dependencies for more independent portability. Encrypt included sensitive data if that workspace's selected protection policy requires it. Offer an explicit inventory and missing-dependency check during import.

For users who select concealment, provide optional application-owned inconspicuous container names such as `.files` or opaque `.state-<id>.files` and lightweight *visual* system-file-style mockups. These are not real OS files and must never modify real system folders; dot-prefix visibility differs by platform, especially on Windows. Fake-looking names/hidden markers do **not** provide cryptographic protection, and browser storage/backups/file sizes may still reveal an object exists. An optional encrypted package can protect documents and sensitive names/coordinates/manifests as selected; choose established authenticated encryption and safe password-derived keys, and avoid putting the key/password in the package.

**Respect the creator's explicit risk choice:** Do **not** force encryption, a password, a recovery route or a second authorization prompt on every Liquid Mode wormhole. A user may intentionally decide that *beating a game alone* is all that is required to reach a non-encrypted desktop, or that they accept relying on a custom ritual or obscured location. Provide optional encryption and recovery tools, explain once in clear Settings language that game/ritual/filename camouflage is *interface gating/obfuscation*, not protection against someone who can access the underlying files/storage, then let the owner choose. Never falsely advertise game-only access as encrypted, browser-exclusive, impossible to bypass, or safe from someone with direct storage access. Conversely, when a user elects encryption, the app should actually enforce its key requirement for decrypting those selected files. The user's choice to omit recovery may make data irretrievable; warn before irreversible setup without secretly overriding their choice.

SNE:OS may provide the intended user interface to the format, but no user-selected encrypted file can be cryptographically guaranteed readable **only** by one particular browser extension: someone possessing the key and understanding the format may implement another reader. Imported custom worlds/scripts must not silently gain privileged access to other users' private files or authorized desktop actions.

## 11. Liquid Mode and programmable wormholes

**Wormholes** are specialized linked locations/events in the shared registry, attachable to canvas XYZ, a world surface or a custom 3D object. Their visual assets and destination actions are interchangeable. In the editor a user can choose direct travel, 2D/3D game, cinematic, puzzle, docking sequence, conditional route, or Custom/Liquid Mode script.

A wormhole can launch an entire game as the journey to a user's workspace. **For game-only spaces, the creator can decide that completing the game is sufficient to navigate to and open that space, with no additional password imposed by SNE:OS.** Custom scripts can also choose a phrase, arrangement, spoken input, orbital condition or other rule. More cautious users can elect to encrypt the underlying files and require credentials; these are optional, separable tools. The editor should visibly distinguish presentation/navigation-only gates from encrypted storage.

Expose actual compatible scene-graph libraries and module capabilities to advanced creators where feasible, but do not evaluate imported arbitrary JavaScript in the extension's privileged DOM. Liquid Mode needs an actually isolated runtime with a small documented, explicit capability bridge to open authorized worlds/workspaces, save asset references, navigate and request permission. The user may opt to lock themselves into an elaborate game route, but app crashes, malicious imported code, or extension privilege escalation must not be disguised as harmless flexibility. Preserve the user's deliberately chosen access and recovery policy. Standard users accomplish common routing without code; programmers can build richer games, scripts and complete alternate environments.

## 12. Implementation order and tests

**M0 — True black substrate:** no white flashes with scrollbars, expanded canvas, first paint, hidden toolbar, load failure or starfield error. Existing black-background fix on the current branch needs browser-visible acceptance tests and correction if still seen.

**M1 — Single-world anchor proof:** build the raycast + circular ownership-zone resolver; create two object-local linked surface points and one canvas point, cover/uncover canvas point with a movable object, save/reload/rotate/zoom, link to real 2D scene and authorized workspace, see/edit/test all points. Respect editor context menus and the existing optional World Key. **Do not advance before the one-world linking flow works end to end.**

**M2 — Sparse universe/ship baseline:** stable XYZ location registry, global canvas location placement, dock and parked/free-flight modes, lightweight empty-space travel, local-only star zones, directional targeting, ≤1-second menu quick-travel effect with instant/reduced-motion options. Keep document editing independent of flight controls.

**M3 — Three worlds:** one selected full model and two left/right dark proxies; consistent/default or seeded spacing, collision-clear layout, shared-coordinate representation handoff and camera alignment, configurable smooth curved switching. Validate slow/missing full assets and low-memory GPU behavior.

**M4 — Portability/privacy:** workspace-only reference scan/rebind, optional complete file package, true consent-based encryption and independent game-only/hidden/camouflage choices, missing-source diagnostics, import collision/coordinate options, explicit permissions and optional recovery behavior.

**M5 — Orbital system + deeper navigation:** deterministic safe orbits, freeze/replan, orbital chart, ship Z/depth controls and manual hyperdrive to a fixed/orbiting target, optional proximity warning/collision effects.

**M6 — Liquid wormholes and creator tools:** configurable game/puzzle/ritual routes, custom scripts in a properly isolated runtime, asset replacement and permissions, optional richer lighting/particles/sound and low-end/high-end rendering profiles.

**Acceptance principle:** The person can always tell which *real file or workspace* a configured destination references, decide whether a location is visible/hidden, move objects to conceal/reveal pre-existing canvas points, dock or hyperdrive to actual XYZ coordinates, and freely choose a playful access ritual versus optional genuine file encryption. The illusion can be elaborate; the underlying data identity, performance costs, and advertised security properties must be accurate.
